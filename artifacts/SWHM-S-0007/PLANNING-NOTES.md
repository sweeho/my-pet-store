## Decisions

### D1 — A 404 says _why_: `reason: "not-found" | "missing-translation"`

`routes/api/catalog/items/[itemId].get.ts:14` and its category and product siblings answer a bare
404 for an unknown id **and** for an existing entity with no details row in the requested locale.
The idea requires those two to look different to a customer: _"An item with no content in the chosen
language shows that same message; an unknown item id still shows the Not Found page."_

The idea's own § Technical Approach proposes solving this client-side ("by the item page when the
fetch 404s under a non-default locale") and states "No server change". **That cannot satisfy the
criterion it sits next to.** Under `ja_JP`, an unknown id and an untranslated item produce the
identical 404, so a client rule keyed on "the locale is not the default" reports every unknown id as
untranslated — which is the failure the criterion exists to prevent.

The layer holding the entity row is the only one that knows the difference, so the 404 body gains a
`reason` discriminator. Status codes and error text are unchanged, so a consumer that ignores the
field sees no difference, and under `en_US` the reason is always `not-found`.

A double-fetch in the client (retry under `en_US`; if that succeeds the entity exists) was the
alternative. It was rejected: it doubles the request count on the unhappy path, it leans on
`en_US` completeness being universally true rather than merely seeded, and it puts a data-layer fact
behind two round trips to infer it.

Promoted to `ARCHITECTURE.md § Key Decisions` — it binds every later localized read (orders, cart,
notifications all face the same question).

### D2 — The active locale is resolved in one place, in a fixed order

`?locale=` → `petstore_locale` cookie → signed-on `profile.preferredLanguage` → `en_US`, decided
inside `useCatalogLocale()` and nowhere else. The URL comes first so a screen in a language can be
shared or bookmarked (the idea's first open question, answered yes). The cookie comes before the
profile so a visitor's choice survives a reload, and so a signed-on customer who switches sees the
new language immediately rather than after the profile round trip lands. `Accept-Language` is not
consulted — the idea's Out of Scope excludes it, which is also why S6 below is not a defect.

Promoted to `ARCHITECTURE.md § Cross-cutting constraints` — every later localized screen inherits it.

### D3 — The unavailable-in-this-language state names the language and offers one click back

Not a generic "no results". The mockup's copy is the contract: heading _"No products in 中文 yet"_,
a body that says nothing has gone wrong, a primary **View in English (US)** and a secondary
**Change language**. Recorded in `DESIGN.md § Unavailable content states` because it binds every
later screen that reads localized content, not just this sprint's four.

### D4 — The four catalogue screens stop rendering `null` while loading

`src/pages/catalog/category/[categoryId].tsx:38` (and the same line in the product and item screens)
returns `null` until the first fetch resolves. Two reasons that has to change here rather than in a
follow-up: the language control is required on _every_ catalogue screen, and a screen rendering
nothing has no control on it; and it already contradicts the standing decision in
`ARCHITECTURE.md § Key Decisions` ("A screen gated on a client-side read renders a pending state,
never nothing", authored in change `swhm-s-0006-multi-language-support`) and the pattern in
`DESIGN.md § Loading states`. Folded into SWHM-T-0075, which owns those files anyway.

### D5 — The seed's locale coverage is asserted, not assumed

`zh_CN` exists for categories and deliberately not for products or items — that absence is what the
`mock-catalog-zh-empty` mockup is built on, and the idea's Out of Scope forbids filling it. An
invariant that a whole screen state depends on, and that a well-meaning future edit would "fix",
gets an assertion. SWHM-T-0073 owns it.

### Test harness

**No harness change is owed, and adding one would be the defect.** Every tier this sprint needs is
already configured and already covers the directories the work touches:

- Vitest runs as two projects chosen by path (`vitest.config.ts:34-67`). `catalog/**/*.test.ts` and
  `routes/**/*.test.ts` are already registered in the `server` project (node), which is mandatory —
  they reach `db/client.ts` and its `bun:sqlite` import, and the jsdom project cannot resolve that
  builtin at all. Everything under `src/` runs in `client` (jsdom). **No new top-level directory is
  created this sprint**, so neither project's `include`/`exclude` needs touching; that is the one
  edit a new server-side module would have required.
- Playwright drives its own server on :5178 with `--strictPort` (`playwright.config.ts`), so
  SWHM-T-0076's spec cannot collide with a running dev server.
- Unit tests run under `bun --bun vitest`, not plain `vitest`, for the same `bun:sqlite` reason.

One environment caveat, recorded in `.vortex/agents-generated.md` from SWHM-S-0002 and still true:
the implementation containers ship no Chromium, so the browser tier fails its preflight there. That
is expected — it is not retried and no browser is installed. The browser tier runs in CI on every
ticket branch and again at integration QA, which is where SWHM-T-0076's assertions are observed.

### CI

**No workflow change is owed.** `.github/workflows/ci.yml` already triggers on `push` and
`pull_request` for `vortex/**`, `dev` and `main`, so every ticket mini-PR and the sprint branch get
check runs, and it already runs the full set in one job: doc links, typecheck, lint, unit and
integration tests, build, then Chromium install and the E2E tier. A second workflow would double
every check run on every sprint branch, which `ARCHITECTURE.md § Key Decisions` already settled.

The only CI-adjacent obligation this sprint carries is the doc-links step: the root docs updated on
this ticket must not introduce a relative markdown link to a missing file, and must not link into

## Spec discrepancies

The adopted change was extracted from the legacy Java EE application, so it describes what that
system did. Where this repository differs, the difference is recorded here and on the ticket — never
by editing the delta spec.

**S1 — The Locale type is a string, not `java.util.Locale`.** The change's decisions document
specifies `java.util.Locale` throughout its DAO signatures. Here `type Locale = string`
(`catalog/types.ts:2`). There is no JVM, and every scenario in the delta spec observes only the
locale _string_ (`ja_JP`, `en_US`, `de_DE`), so nothing it specifies distinguishes the two. No
behavioural difference; no work.

**S2 — Boxes 2.1–2.3 are already shipped.** "Add locale column to category_details /
product_details / item_details" was completed in change `swhm-i-0004-product-catalog-search`: each
`_details` table carries `locale text not null` inside a composite primary key `(entity id, locale)`
plus a locale index (`db/schema.ts:89,116,145`). No migration is owed this sprint, and SWHM-T-0073's
criteria require `db/schema.ts` and `drizzle/` to come out unchanged so a redundant migration cannot
slip in.

**S3 — Boxes 3.1–3.3 are already shipped.** "Add Locale parameter to all catalog query methods",
"Update SQL queries to filter by locale" and "Return null for missing locale-specific content" are
all in place: every read in `catalog/catalog.ts` takes a locale, `localeJoin()` (`catalog/query.ts:30`)
is the single definition of the locale predicate so two services cannot filter differently, and the
inner joins make a missing locale row yield `null` (`catalog/category.ts:32`) or `EMPTY_PAGE`
(`catalog/page.ts:4`). SWHM-T-0074's remaining work is D1, not the locale parameter.

**S4 — Boxes 2.4 and 4.1–4.3 ask for content in _all_ supported locales; zh_CN is deliberately
partial.** `catalog/seed.ts` carries `en_US` and `ja_JP` for every category, product and item, but
`zh_CN` for the five categories only. This is not an oversight to close: the idea's Out of Scope
says in terms _"Adding zh_CN product and item content to the seed data"_, and the
`mock-catalog-zh-empty` mockup is a screen that only exists because the content is absent. The gap
is product scope. SWHM-T-0073 pins it as an assertion so it cannot drift in either direction.

**S5 — Box 4.4 resolves to no work.** "Create image variants for locale-specific product images if
needed" — `item_details.image` is already a per-locale column (`db/schema.ts:153`) and the seed
points every locale at the same file (e.g. `/images/birds/african-grey.jpg` for both `en_US` and
`ja_JP`). Nothing in this catalogue's imagery is language-specific, so the conditional resolves to
not needed. The box is tagged to SWHM-T-0075 so the platform ticks it rather than leaving it
permanently outstanding; the ticket's criteria do not ask for it.

**S6 — Box 1.3 says "browser headers"; this sprint will not read them.** The box reads "Detect
locale from user session or browser headers" and the change's decisions document says "Locale
detected from user session or request headers". The idea's Out of Scope excludes _"Detecting a
language from the browser's `Accept-Language` header"_. So 1.3 is implemented as session/profile plus
an explicit in-browser choice (D2), and the header half is dropped by product decision, not by
omission.

**S7 — The delta spec's null scenario uses an unsupported locale, and that works by design.**
_"Missing locale content returns null"_ is written with `de_DE`, which is not in `LANGUAGES`.
`resolveLocale()` deliberately does not reject an unsupported locale (`catalog/locale.ts:10-13`), so
`de_DE` behaves as "a locale with no rows" and the scenario passes exactly as written. Worth naming
because `isSupportedLocale()` is exported and used by nothing but its own test — a future change that
starts gating on it would break this scenario. Under D1 an unsupported locale on an existing entity
reports `missing-translation`, which is the truthful answer.

**S8 — The delta spec has nothing to say about the user interface**, which is where this sprint's
work almost entirely lies. Its decisions document states outright: _"No screen records were
extracted for this capability; its user interface is unspecified."_ The idea's canvas and the three
exported design references in `artifacts/SWHM-S-0007/design/` are therefore the contract for every
screen-level criterion in SWHM-T-0072, SWHM-T-0075 and SWHM-T-0076, and D1–D4 above are decisions
planning had to take rather than read.

**S9 — The catalogue screens contradict a standing decision already recorded in this repository.**
Not a spec discrepancy but found in the same pass: the four screens `return null` while their first
fetch is in flight, against `ARCHITECTURE.md § Key Decisions` and `DESIGN.md § Loading states`. See
D4; folded into SWHM-T-0075.
