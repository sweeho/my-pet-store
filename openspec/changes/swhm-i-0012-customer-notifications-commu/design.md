# Notifications — Design Document

## Architecture

Notifications are triggered by order status changes and sent asynchronously via JMS message queue to a mail server component.

## Notification Types

- Order confirmation (placed)
- Order approved/denied notification
- Order shipped/completed notification

## Email Content

Customer email retrieved from account ContactInfo.email. Message body contains order ID, customer name, and status details.

## Message Queue

AsyncSender EJB sends OrderApproval/OrderNotification messages to mail queue for asynchronous delivery.

## Error Handling

Message delivery failures log errors but don't block order processing.

## User Interface

No screen records were extracted for this capability; its user interface is unspecified.

## Decisions

- **D1 — `notifications/` is a new top-level capability directory.** Server-side code that is not an endpoint cannot live under a directory Nitro scans, and its tests must be registered in Vitest's `server` project include and the `client` project's exclude (F10). This is an application of the standing capability-module rule, not a new one.
- **D2 — The queue is the existing `notifications` table, extended, not a new table.** The approval capability already writes rows to it and its tests assert the shape (F1, F2). Delivery state is added as columns — a status defaulting to `QUEUED`, a nullable sent timestamp, a nullable failure reason — with the generated migration committed. A parallel table would leave the rows the shipped path writes unreadable by the path that sends them.
- **D3 — One entry point, called by the transition; the module never watches.** `notify(orderId, kind)` is the only way a row is queued, and the three transitions call it: the decision applier for `APPROVAL` and `DENIAL`, the completion point for `COMPLETION`. The existing `order/notification.ts` is superseded by it rather than kept alongside it (S4).
- **D4 — The queue is drained on the request that queued it, after that request's transaction has committed.** Nothing schedules a run and no endpoint of its own is introduced. The alternatives were a Nitro task (this repository has never run scheduled work, and `tasks/` does not exist) and a dispatch endpoint mirroring fulfilment's (a second admin-protected surface, and a notification nobody sends until somebody asks). Draining after commit satisfies the async requirement as the scenario states it — the status update completes without waiting for delivery — and makes "an email notification SHALL be sent" observable from the same request rather than only from a test that calls the dispatcher directly.
- **D5 — A notification's recipient is resolved when it is sent, not when it is queued.** The address comes from the account's contact record at send time, falling back to the address copied onto the order when the account holds none, and the row is marked undeliverable when neither exists. This is a deliberate, narrow exception to the rule that a later capability reads the order rather than joining back to the account: that rule protects what was **agreed** — a price, an address an order shipped to, the locale it was judged under — and a notification is none of those. It is a contact action taken now, and writing to an address the customer has since replaced fails in the one way the capability exists to prevent. The requirement observes exactly this (S3).
- **D6 — Delivery is at-most-once.** A transport failure marks the row failed with a reason and logs it (F12); nothing retries, nothing backs off, nothing dead-letters. This is what the spec asks for and what the idea accepts. An account with no address is marked undeliverable, which is terminal and distinct from a failure (S6).
- **D7 — A drain pass is safe to repeat, by status.** Only queued rows are picked up, and each is moved to a terminal status in the same pass, so a second run over the same order sends nothing twice. This is the obligation the standing "nothing retries, so the operation must tolerate being run twice" decision transfers to every capability that lost its transport.
- **D8 — The mail transport is an interface with an injected default that records rather than sends.** No SMTP dependency is added and no credentials are held, because the repository has nowhere to put them (F5). The default implementation records what would have been sent, which is what makes "a notification was sent to this address" a fact the tiers below the browser can observe. This is the product's second outward boundary and follows the shape the first one set (F8).

## Phases

1. **Notification service.** The `notifications/` directory and its Vitest registration (the test-harness phase — no other harness work is needed, D1/F10); the delivery columns on the table and the committed migration; `notify()`; recipient resolution from the account; the `COMPLETION` kind and the completion trigger; the approval and denial call sites re-pointed.
2. **Email generation.** The per-kind subject and body builder, over the order and the resolved recipient. Pure — no database read, no transport.
3. **Delivery.** The transport interface and its recording default, the drain pass and its terminal statuses, and the two call sites that drain after their transaction commits.
4. **Verification.** The cross-module integration pass: each of the three transitions through to a sent row, and the missing-address case. No browser-tier spec — this capability has no screen, so nothing about it is observable in a browser (the idea puts a user interface out of scope).

**CI phase:** none. The existing workflow already runs every tier on pushes and pull requests to `vortex/**` branches (F11); this change adds no script, no service and no job.
