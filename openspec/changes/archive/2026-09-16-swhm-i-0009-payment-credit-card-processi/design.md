# Payment Processing — Design Document

## Credit Card Validation

Card number, type, and expiry month/year are required fields validated during checkout.

## Expiry Validation

Cards must not be expired. Expiry is checked against current date during authorization.

## Card Acceptance

Card types (Visa, MasterCard, American Express) must match accepted list.

## Payment Authorization

Card information is validated but authorization/processing is delegated to external gateway.

## User Interface

No screen records were extracted for this capability; its user interface is unspecified.

## Decisions

- **D1 — No card number is persisted, and this change adds no column, no migration and no encryption.** It extends the standing decision in `ARCHITECTURE.md § Key Decisions` rather than revisiting it. See S1, S2.
- **D2 — The store's own `CARD_TYPES` stand; Visa, MasterCard and American Express are not adopted.** `payment/` imports the list from `account/vocabulary.ts` and never redefines it, so there remains exactly one place the accepted types are written down. See S4.
- **D3 — `payment/` is a new top-level capability directory**, following the standing rule that server-side capability code lives outside the directories Nitro scans. It is registered in the Vitest `server` include, the `client` exclude and `tsconfig.node.json` — all three, because registering in one is the known failure mode (F9).
- **D4 — The expiry check lives in `payment/expiry.ts` and distinguishes a missing expiry from an expired one.** `account/card.ts`'s accessors and their `01`/`2010` fallbacks are untouched: an archived scenario asserts them (F3, F14), and a fallback that reads as expired is exactly why the check cannot be built on them.
- **D5 — The processor is an interface with an injected implementation, defaulting to a deterministic stub.** A stub keeps "an authorization request was sent" observable at every tier without a network call, and keeps the decline path (mockup State C) testable. See S6.
- **D6 — Authorization precedes order placement, and a decline leaves no order.** This is the only sequencing consistent with the mockups, whose declined state reads "No order was placed and the card was not charged". `POST /api/order` is called unchanged, after authorization succeeds — the order contract does not move, only what happens before it.
- **D7 — The in-flight submit state is documented once, in `DESIGN.md`.** This is the product's first irreversible action with an observable pending state (F12), and a pattern decided per screen is a pattern three screens disagree about — the same reasoning that put the per-field invalid state there during `swhm-i-0008`.
- **D8 — `payment/types.ts` is written whole by the first ticket and never extended by a later one in this sprint**, the rule adopted after three tickets appended to one shared type file with no dependency edge between them.

## Phases

1. **Payment module, card types and storage path** — `payment/types.ts` written whole, the module's three registrations, and the storage path confirmed against `card_metadata` with no schema change (D1, D3, D8). (SWHM-T-0175)
2. **Card validation** — `payment/expiry.ts` distinguishing missing from expired, and `payment/validation.ts` checking the type against the store's list (D2, D4). (SWHM-T-0176)
3. **Authorization boundary, payment screen and checkout sequencing** — the processor interface and its stub, `POST /api/payment/authorize`, the `/payment` screen and its protected-resource entries, the order form's submit re-pointed at the payment step, and `e2e/order.spec.ts` kept green through it (D5, D6). (SWHM-T-0177)
4. **Browser coverage for the payment journey** — `e2e/payment.spec.ts`: the refusal, the in-flight state and the decline (S8). (SWHM-T-0178)
5. **Test harness** — no new harness is required. Vitest's two projects already cover both tiers and Playwright already covers the browser; the only registration this change owes is `payment/**` in the `server` include, the `client` exclude and `tsconfig.node.json`, which is phase 1's work (F9, D3). Module tests sit beside the modules they cover; the payment screen's test is a `client` test because it lives under `src/`.
6. **CI** — unchanged and verified, not assumed: `.github/workflows/ci.yml` already triggers on push and pull request to `vortex/**`, `dev` and `main`, and its single job runs lint, typecheck, the unit tier and the browser tier with a real Chromium (F10). No ticket in this sprint edits it.

## Design references

Exported from idea SWHM-I-0009 (doc version 8, frozen) to `artifacts/SWHM-S-0016/design/`: `wireframe-checkout-payment-details.html`, `wireframe-checkout-payment-details-validation-and.html`, `mockup-checkout-payment-details.html`, `mockup-checkout-payment-details-validation-and.html`, with `MANIFEST.md` alongside them. These are the authority for the payment screen, and they contradict this change's own `## User Interface` section (S5).

The two "validation and authorization states" files are the ones that fix behaviour: **State A** is a validation refusal, rendered per field, with nothing sent to the processor; **State B** is the request in flight, with the submit control disabled and reading "Authorizing…"; **State C** is a processor decline, which leaves no order and charges nothing (D6). Build the payment screen from the mockups, not from the wireframes — the wireframes carry the same layout without the states.
