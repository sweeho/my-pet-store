# Design — SWHM-S-0022 bugfix

Measured on the sprint branch `vortex/sprint/swhm-s-0022-75bc2a59` at planning time. Every figure below was read from the repository or from a build of it, not carried over from the defect reports.

## Findings

- **F1 — both files are live routes in a production build.** `bun run build`, then reading the route table out of `.output/public/assets/index-*.js`, yields these generated paths: `*`, `/`, `:categoryId`, `:itemId`, `:productId`, `NotFound`, `RootErrorBoundary`, `about`, `admin`, `cart`, `catalog`, `category`, `customer`, `enter-order-information`, `inventory`, `item`, `order-completed`, `orders`, `orders-approval`, `payment`, `product`, `reports`, `revenue`, `signon`, `signon-failed`, `signon-welcome`, `supplier`, `user-creation-error`. `NotFound` and `RootErrorBoundary` are there; `UnavailableInLanguage` is not, which is the exclusion mechanism working.
- **F2 — the exclude list covers tests and one component.** `vite.config.ts` § `Pages`: `exclude: ["**/*.test.tsx", "**/*.test.ts", "**/UnavailableInLanguage.tsx"]`, the last entry carrying a comment explaining that the file is a shared component rather than a route (SWHM-T-0075). That is the precedent this fix follows.
- **F3 — `RootErrorBoundary` has no live consumer.** `grep` across `src/` finds it only in its own file. `src/main.tsx` renders `useRoutes(routes)` inside a `Suspense` and wires no `errorElement` anywhere. The only description of the intended wiring is `src/App.md`, an illustrative template document that nothing compiles.
- **F4 — the catch-all imports `NotFound` by relative path.** `src/pages/[...all].tsx` is exactly `export { default } from "./NotFound";`. Excluding a file from route generation does not affect module resolution, so the re-export keeps working; **moving** the file does not, and would have to be updated in step.
- **F5 — the catch-all is what makes an unrouted path render the not-found screen.** `path:'*'` is in F1's route table, and `e2e/legacy-routes.spec.ts` (SWHM-T-0082) already asserts `/users`, `/users/1` and `/users/profile` resolve that way after the same class of fix.
- **F6 — no unit test can see file-based routing.** `vitest.config.ts` mirrors only the React plugin, the `@` alias and AutoImport, with an explicit comment that file-based routing is intentionally left out. The `~react-pages` virtual module does not exist under Vitest.
- **F7 — the two existing repository-level conformance tests read source as text.** `src/layout-width.test.ts` and `src/palette-classes.test.ts` both enumerate files (`git ls-files src/pages`) and `readFileSync` them, asserting a property of the codebase rather than of a rendered component. `src/theme-tokens.test.ts` is the original of the pattern.

## Decisions

- **D1 — exclude the two files from route generation; do not move them.** `Pages({ exclude })` gains `**/NotFound.tsx` and `**/RootErrorBoundary.tsx`, following F2's precedent. Moving both to `src/components/` was the alternative: it is a larger diff, it breaks F4's re-export and the `src/App.md` reference until both are updated, and it does not remove the fault class — the next component parked under `src/pages/` is still a public URL. D3 removes the class instead, which is the part worth paying for.
- **D2 — both paths then render the not-found screen through the catch-all.** No route is added and no redirect is introduced: an excluded file simply stops generating a route, and F5's `path:'*'` already answers every unrouted path. `/NotFound` keeps exactly one address — the one any unrouted path resolves to.
- **D3 — the guard is a checked-in route inventory, not a pattern match.** Nothing in a file's text distinguishes a screen from a component, so a heuristic would either miss the next case or flag a legitimate one. The guard enumerates `git ls-files src/pages` (`.tsx`, excluding `*.test.tsx`) and requires every file to appear in exactly one of two checked-in lists: the intended screens, or the files named in `vite.config.ts`'s exclude list. A new file under `src/pages/` fails the unit suite until its author classifies it. This is the countermeasure to the fault `ARCHITECTURE.md` § Routing already names — "a page survives by being forgotten" — and it makes that section's "nothing lists routes anywhere" false on purpose.
- **D4 — the guard reads `vite.config.ts` as text rather than sharing a constant with it.** A module imported by both `vite.config.ts` and a test under `src/` would cross a project boundary: `tsconfig.json` owns `src` and `tsconfig.node.json` owns `vite.config.ts`, and both are part of a `composite` build. Reading the config file as text is the technique F7's two existing guards already use, and it costs no build-graph change.
- **D5 — the behavioural assertion goes in the browser tier.** F6 rules out a unit test that navigates. `e2e/legacy-routes.spec.ts` is the right home rather than a new spec file: it exists to pin exactly this — paths that were reachable and should not be — and its `/users` block and this one share a rationale. One `test.describe` block, two paths, asserting the not-found heading is visible and the error-boundary copy is absent.
- **D6 — `RootErrorBoundary.tsx` stays.** It is dead (F3) and excluding a dead file keeps it alive behind an exclusion comment, which is not tidy. Deleting it is nonetheless a different decision from the one this defect asks for, it would take `src/App.md`'s example with it, and the defect's own acceptance criterion asks for the path to render the not-found screen rather than for the file to be gone. Recorded under § Open questions instead.

## The platform defect — SWHM-T-0235

Re-verified against `/app/packages/core/src` (`@vortex/core@7.2.0`) rather than trusted from the report. Every cited line matches:

- `a2a/agent-tools.ts:153` — `if (ctx.codebaseId) env[A2A_ENV.codebaseId] = ctx.codebaseId;`. A falsy context silently omits `VORTEX_A2A_CODEBASE_ID` from the spawned run's environment instead of failing.
- `agents/harness-service.ts:369` — `const runCodebaseId = args.codebaseId ?? bundle.codebase_id;`, above the comment stating that GLOBAL FSM agents carry a NULL `codebase_id` and the work belongs to the ticket's codebase. The caller must pass `codebaseId` explicitly for such an agent.
- `agents/global-agent-seeder.ts` — global agents are seeded with `codebase_id IS NULL`, so `planning` has no codebase of its own to fall back to.
- `a2a/tools.ts` § `a2aSendMessageTool` — no `if (!codebaseId) throw` guard, unlike its siblings; `assertValidRole` calls `listTeamRoleKeys(ctx.codebaseId ?? '')`, which is the empty string that reaches Postgres and produces `invalid input syntax for type uuid: ""`.
- `a2a/agent-heartbeat-orchestrator.ts` § `setIntegratorDispatcher` — passes `codebaseId: req.codebaseId` under a comment marking it REQUIRED "for the live bug this closes". The same bug, already fixed once on a different dispatch path.

**One finding the report could not reach.** `a2a_assign_ticket` (`a2a/tools.ts`) does not dispatch a run at all — it resolves the slug to a concrete agent row and updates the ticket to `ASSIGNED`. The run is started separately and idempotently by `wakeAssignedAgentsActivity`, named in `scheduler/assignment-record.ts` and `fsm/actions.ts` but **defined in neither** — it lives in the Temporal worker package, which is not present in this runtime image. So the omission is in that activity's call into `dispatchHarnessRun`, not anywhere in `@vortex/core`, and `@vortex/core` is itself only an unpacked install at `/app` with no git repository or remote.

- **D7 — nothing about this defect can be fixed from this repository, so nothing is attempted.** An implementation ticket here could only edit a container-local copy of an installed package: not committable to this sprint branch, not visible to CI, discarded when the container is recycled. The ticket is refined with the finished diagnosis and deferred with that reason, rather than spending a dispatch on work that must end blocked. Its practical mitigation needs no code: dispatch an FSM role through the scheduler's own sweep rather than a manual `a2a_assign_ticket`, which is the contrast the report already isolated.

## Open questions

- **O1 — `RootErrorBoundary.tsx` is dead code behind an exclusion (D6, F3).** The product has no error boundary wired; the file describes one nobody renders. Whether to wire it or delete it is a decision for a sprint that is actually asking about error handling.
- **O2 — `src/App.md` documents routing the application does not do.** It shows an explicit `<Route>` table with `errorElement`, which `src/main.tsx` has never used. It is illustrative and uncompiled, so it misleads only a reader, but it is the only place the intended `errorElement` wiring is written down.
- **O3 — the route inventory is maintained by hand (D3).** It could be generated from the same source the plugin reads, at the cost of reimplementing the plugin's path mapping. Worth revisiting only if the inventory starts drifting in practice.
