# Architecture

See [PRODUCT.md](./PRODUCT.md) for what this is, [DESIGN.md](./DESIGN.md) for the visual system, [README.md](./README.md) for worked examples of every pattern below.

My Pet Store is a single deployable: one Vite process serves a React SPA and a Nitro API together in development, and one Nitro server output serves the built application in production. There is no separate frontend host, no separate API service, and no external datastore. The screens the store's operator uses are part of that same deployable, not a second application.

## Stack

- **Framework**: Vite 8 running a React 19 SPA + a Nitro 3 server together
- **Language**: TypeScript 5 (strict)
- **Frontend routing**: `vite-plugin-pages` (file-based) + `react-router` 8
- **Backend routing**: Nitro 3 / H3 2 (file-based)
- **Database**: SQLite via Bun's built-in `bun:sqlite` + Drizzle ORM — schema/client in `db/`, migrations in `drizzle/`. Requires the Bun runtime in dev, test and production (see Deployment)
- **Styling**: Tailwind CSS v4, CSS-first — tokens live in CSS, not in a config file. (`tailwind.config.ts` exists as an empty tracked file inherited from the template and is read by nothing.)
- **UI primitives**: shadcn/ui-style — Radix Slot, `class-variance-authority`, `cn()`
- **Icons**: `lucide-react` for general use; `@headlessui/react` supplies the overlay primitives the language menu is built from. `@heroicons/react` is still a declared dependency but has no consumer in `src/` now that the shared header has replaced the home page's mobile navigation dialog; removing it is a decision that has not been taken.
- **Auto-imports**: `unplugin-auto-import` — `react` + `react-router` need no import
- **Type**: the platform system stack, via Tailwind's default `--font-sans`. The application ships and fetches no web font — see § Cross-cutting constraints and [DESIGN.md](./DESIGN.md#brand-mark)
- **Tests**: Vitest + Testing Library (unit/integration/UI), Playwright (E2E/smoke)
- **Lint/format**: ESLint 9 + typescript-eslint, Prettier, Husky + lint-staged

No charting or data-visualisation dependency is present. Where the product reports figures it draws them from the primitives above; adding one is a decision that has not been taken.

## Routing

**Frontend**: `src/pages/**/*.tsx` → routes (`about.tsx` → `/about`, `[id].tsx` → `/:id`, `[...all].tsx` → catch-all). `*.test.tsx` excluded via `Pages({ exclude })` in `vite.config.ts`.

**Backend**: `routes/api/*.ts` → `/api/*`, `middleware/*.ts` runs first and can set `event.context`. Requires `nitro({ serverDir: "./" })` in `vite.config.ts` — the default is `false`, which scans nothing. `*.test.ts` excluded via `nitro({ ignore })`.

Creating the file is the whole registration step on both sides; nothing lists routes anywhere. The
converse holds too and is easier to miss: **a page file nothing links to is still a public screen.**
There is no manifest whose absence would flag it, so a page survives by being forgotten — which is how
the bootstrap template's example screens stayed reachable for seven sprints. Removing a screen means
removing its file. This cuts hardest for a screen that is meant to be restricted: an administrative
page is protected because its path is in the resource list, never because nothing links to it.

Nitro scans `api/`, `routes/`, `middleware/`, `plugins/` and `tasks/`, and auto-imports from `utils/**`. **Server-side code that is not an endpoint must live outside those directories** — a `.ts` file under `routes/` becomes an HTTP route whether or not it exports a handler. That is why capability modules get their own top-level directory — `auth/`, `account/`, `catalog/`, `admin/`, `cart/`, `order/`, `payment/`, `fulfillment/` and `notifications/` — and why a new one must not be named `utils`.

## Data model

Defined in `db/schema.ts`:

- **users** — `id` (autoincrement pk), `name`, `email` (unique). Template demo content, seeded by `db/client.ts` and probed by `e2e/smoke.spec.ts`; not a product decision (PRODUCT.md § Not yet decided).
- **auth_users** — `user_name` (pk), `password`, `role`. The authenticated customer, and the one place the product records that an identity may act administratively. Deliberately distinct from `users`: the demo table has no credential column and a numeric key, and its routes are regression cover that a repurpose would destroy. → `openspec/specs/user-authentication/`, `openspec/specs/admin-operations/`
- **sessions** — `id` (pk), `j_signon`, `j_signon_username`, `original_url`, `updated_at`. Per-visitor server-side state; the attribute names are the ones the authentication specification asserts. `updated_at` is written on every session write and read by nothing: sessions do not expire, for anyone (PRODUCT.md § Not yet decided).
- **customers**, **accounts**, **profiles**, **contact_info**, **addresses**, **card_metadata** — what an account holds beyond credentials. Every one of them is keyed on `user_name` and foreign-keys upward with `ON DELETE CASCADE`: the relationships are 1:1 the whole way down, so a shared primary key carries them and no surrogate id is introduced. `customers.user_name` references `auth_users.user_name`, which keeps the credential row as the identity. `card_metadata` holds a card type, an expiry and four digits — see § Key Decisions. → `openspec/specs/account-management/`
- **category**, **product**, **item** and their **\_details** siblings — the catalogue. The hierarchy is 1:N downward (a category holds products, a product holds purchasable items), which is why each carries its own key rather than sharing one. Each entity is split from its translatable content: `category` holds the identifier, `category_details` holds one row per locale with the name and description, and the pair is keyed on (entity id, locale). That split is the whole localization mechanism — content for a locale either exists as a row or does not, so a read in an unsupported locale returns nothing without a branch anywhere in code. Because the entity row and the detail row are separate, a read that finds nothing can also say which of the two was missing, which is what lets a screen tell an untranslated thing from a thing that does not exist. → `openspec/specs/catalog-browsing/`, `openspec/specs/internationalization/`
- **orders**, **order_line_item** — an order and what was in it. `orders` carries its own `order_id` because the relationship to the customer is 1:N, not 1:1, which is the distinction § Key Decisions draws for every entity below the account. It also carries a billing address, a shipping address and the contact details the order was placed with — copied onto the order, never referenced from the account, for the reason § Key Decisions gives. A line item is keyed on (`order_id`, `line_number`) and records the **price paid**, along with the `catid` and `productid` the item sat under when the order was placed, rather than referencing any of the three as they stand today. These tables were defined by the administrative capability because it was the first to need them; the capabilities that create orders inherit the shape rather than redefining it. `order_id` is allocated by SQLite's `AUTOINCREMENT` and the sequence is seeded at startup so the first order allocated in an empty table is 1001, which the extracted specification requires — there is no separate identifier service. `orders` also carries the `locale` the order was placed under, copied from the customer's profile at placement for the same reason its addresses are: the figure an order is judged against depends on its locale, and resolving that at decision time would let a customer move their own order across a threshold after the fact. It is nullable, because every order placed before the approval capability existed has none and a null means "no threshold applies" rather than a value to invent. → `openspec/specs/order-placement/`, `openspec/specs/admin-operations/`, `openspec/specs/fulfillment-management/`, `openspec/specs/order-approval/`

- **inventory** — how many of an item the store holds. `itemid` (pk, referencing `item`) and a quantity, and nothing else: no reservation column, no ledger and no history, because the product records what is held now rather than how it came to be that. An item with no row reads as zero rather than as an error, so stocking an item is one write and adding a catalogue item stays a one-table operation. It is the only table this capability introduced; the shipped quantity and the order status it also needs were already columns on the two tables above. → `openspec/specs/fulfillment-management/`

- **supplier_po**, **supplier_po_line_item** — the order the store places with its supplier once an order is approved. One PO row per approved order, keyed on the order it came from, holding the PO date and a copy of the shipping address; one line row per order line, holding the category, product and item it names, the quantity and the price. Every field is copied from the order rather than joined back to it, for the same reason the order copies from the account. A PO is written once, by the approval that produced it, and nothing rewrites one — which is what makes re-deciding an order safe to repeat. It is the fulfilment capability's inbox and not an outward boundary; see § Integration points. → `openspec/specs/order-approval/`

- **notifications** — what the store owes a customer and what became of it, never the message itself. A row records the order, the kind of outcome (an approval, a denial or a completion), the address the order was placed with, when it was queued, and then how it ended: sent with a timestamp, failed with a reason, or undeliverable because the account holds no address. It is an outbox, and it is deliberately the queue this capability was specified with a broker for — see § Key Decisions and § Integration points. The row's terminal status is what makes a drain pass safe to repeat and what makes "this customer was told" a durable fact rather than an event that happened once in a log. The address the notification is actually sent to is resolved from the account when it is sent, not read from this row; the column is the fallback for an account that has none. The body is not stored — it is assembled at send time from the order and the account, so nothing here can disagree with either. → `openspec/specs/notifications/`, `openspec/specs/order-approval/`

- **cart_items** — what a visitor has chosen but not yet bought. Keyed on (`session_id`, `itemid`) and holding a quantity and nothing else: the composite key is what makes adding an item already present a single upsert, and the absence of a price column is what stops a cart from ever disagreeing with the catalogue about what an item costs. The line's price, its total and the cart's subtotal are all derived when the cart is read, never stored — a stored total is a second source of truth that drifts the first time an operation forgets to update it. The cart is reachable only through the session row it references, which is what makes it session-scoped without a second mechanism. → `openspec/specs/shopping-cart/`

Routes import `db` and the table objects directly (see `routes/api/users/`) — there is no repository layer, and adding one is a decision that has not been taken.

- Prices (`item.list_price`, `item.unit_cost`, `order_line_item.unit_price`) are stored as `real`, matching the extracted specification's `double`. Reporting sums them and rounds at the response boundary, which is the first money arithmetic in the product; it is a working choice, not a settled representation — see ticket SWHM-T-0058.

- **`ON DELETE CASCADE` in this schema documents intent and enforces nothing.** SQLite disables foreign-key enforcement by default and `db/client.ts` never sets `PRAGMA foreign_keys`, so every cascade declared above is inert at runtime. Declare them anyway — they state the ownership a reader needs — but never rely on one firing: code that must remove dependent rows removes them itself. Turning the pragma on is a single change that would alter delete semantics for every table at once, so it is a decision to take deliberately, with tests, rather than as a side effect of some other work.
- After editing `db/schema.ts`, a migration must be generated into `drizzle/` and committed; the schema change is not complete without it.
- The database file is `sqlite.db` at the project root — gitignored, created on first run. The `drizzle/` migrations are committed.
- Under Vitest (`VITEST=true`), `db/client.ts` swaps in an in-memory database, so tests never touch the development database.
- `db/client.ts` resolves both `sqlite.db` and the migrations folder from `process.cwd()`, not `import.meta.url` — Vite, Nitro and Vitest all transform the module, so its `import.meta.url` is not a real `file://` URL.
- `db/client.ts` also seeds development data, including the administrator account. That account is development seed data and PRODUCT.md § Not yet decided records it as something to settle before a real deployment.

## Request flow

`GET /api/hello`: `middleware/auth.ts` attaches a user to `event.context` → `routes/api/hello.ts` reads it and responds. `routes/api/users/[id].ts` shows the dynamic-route and `createError()` 404 pattern against a real Drizzle query.

`middleware/auth.ts` is a stub that attaches a hardcoded user to every request. It is not authentication and nothing may treat it as such.

Authentication is `middleware/signon.ts` and the handlers under `routes/api/signon/`. A request carries its session in an httpOnly cookie; the middleware resolves it, asks `auth/signon-filter.ts` whether the path is reachable, and on a denial answers instead of running the handler. How it answers depends on who asked and on why it was denied: a navigation by someone not signed on is sent to the sign-on page with the requested path recorded as the destination to return to, a request the page issued in the background is answered 401 and records nothing, and a request from someone who is signed on but lacks the role required by the path is refused outright — see § Key Decisions for why the last of those is not a redirect.

Administrative endpoints under `routes/api/admin/` are reached through that same middleware and then apply one shared guard in `admin/request.ts`, rather than each repeating the role check.

## Integration points

The application talks to no third-party service at runtime. Every asset it serves comes from its own origin (§ Cross-cutting constraints), its data is its own SQLite file, and it declares two outward-facing boundaries, neither of which currently reaches anything.

- **Payment processor** — `payment/processor.ts` declares an interface and takes an implementation by injection; the default is a deterministic stub that decides locally. No network call is made, no credentials are held, no processor is chosen, and nothing settles: the boundary exists so that "an authorization was requested" is a fact the application can produce and observe, and so that the day a real processor is integrated, one module changes. This is the point at which a real card number would leave the application, and the reason the store never stores one — see § Key Decisions. → `openspec/specs/payment-processing/`

- **Mail transport** — `notifications/transport.ts` declares an interface and takes an implementation by injection; the default records the message it was given rather than delivering one. No mail provider is integrated, no dependency is added and no credentials are held — the repository has nowhere to hold one (PRODUCT.md § Not yet decided). What the boundary buys is that the store's decision about _what to say, to whom, and when_ is complete and observable below the browser tier, and the day a provider is chosen, one module changes. → `openspec/specs/notifications/`

Anything that reaches outside this application gets an interface here, an injected implementation, and a stub the tiers below the browser can run against. Both boundaries above are that shape, and neither was a detail of the capability that introduced it.

Three things that look like boundaries are deliberately not ones. **Fulfilment has no queue**: the legacy application received purchase orders on a JMS queue, and this one receives a request — see § Key Decisions. **The invoice a fulfilment run produces goes nowhere**: it is returned to the caller as a string, and nothing stores, sends or renders it, because no trading partner exists to receive one (PRODUCT.md § Not yet decided). **The supplier purchase order an approval produces is a table, not a transmission**: the legacy application serialized it to XML and put it on a supplier queue, and here it is a row in the same database, recording the approval that released the order for fulfilment. What fulfilment then keys on is the order's own approved status, not that row — see § Key Decisions. No trading partner exists on the far side of it either, so there is nothing to serialize a document for. None of the three is a boundary until something is on the other side of it.

The same reasoning, one step further on, is why a queued notification is a row rather than an email. That row is now read: the notification capability drains it and hands each message to the mail transport above, which is the boundary its delivery needed and the second entry in this section. The two halves stayed separable exactly because the handoff between them was a table — the capability that queues a notification still does not know that anything sends one.

## Cross-cutting constraints

- **The Bun runtime is mandatory wherever `db/client.ts` loads.** It imports the `bun:sqlite` builtin, which Node cannot resolve. This is why the test script runs `bun --bun vitest`, why Playwright's web server names Vite's bin file under `bun --bun` rather than going through a shebang, and why the production process manager sets Bun as its interpreter. A path that loses `--bun` breaks every database-backed route while static pages and non-database routes stay green — the failure is silent by construction, which is why `e2e/smoke.spec.ts` probes a database-backed route deliberately.
- **Per-visitor state lives in the database, not in the process.** H3 2 ships cookie helpers but no session primitive, so the session is a row keyed by an opaque id in an httpOnly cookie. Anything that needs to remember something about a visitor between requests reads and writes that row rather than a module-level map, which would not survive a restart and would not be shared across processes.
- **Access control is decided in one pure function and enforced in two places.** SPA navigation never reaches the server, so a server-only filter would protect an API path and silently leave the equivalent page open in development, which is exactly where the browser tier runs. A new protected resource is added to the configuration, never as a new check. The function answers two questions, not one — is this identity signed on, and does it hold the role this path requires — because a product with a privileged surface needs to tell "you are not signed on" from "you are, and it is not yours". Refusing a request and remembering where to send the visitor back are separate decisions: the second applies only to a navigation, because a protected path is also fetched in the background by screens the visitor never asked to leave.
- **Every asset the application serves comes from its own origin.** No page references a font, mark, icon or stylesheet on a third-party host — the standing rule is [DESIGN.md § Brand mark](./DESIGN.md#brand-mark), and it holds for build-time injections as much as for markup, which is where it has twice been broken. The same applies in the other direction: where content the application ships names an asset location, the asset is in the repository. Both are observed in the browser tier, because a build-injected `<head>` link and a 404 on an image the page recovers from are invisible to every tier below it.
- **The language a visitor reads is resolved in one place, in a fixed order**: the `locale` search parameter, then the `petstore_locale` cookie, then a signed-on customer's `profile.preferred_language`, then `en_US`. That order lives inside `useCatalogLocale()` (`src/pages/catalog/shared.ts`) and nowhere else, and every localized read takes the result as an explicit parameter rather than reading ambient state. The order is not arbitrary: the URL leads so a screen in a language can be shared or bookmarked, and the cookie precedes the profile so a visitor's choice survives a reload and a signed-on customer's switch applies before the profile round trip lands. A second resolution site is how two screens come to disagree about what language the visitor is reading. The browser's `Accept-Language` header is deliberately not consulted — see PRODUCT.md § Scope.
- **One hook reads the catalogue, and it surfaces why a read failed.** Every catalogue screen fetches through `useCatalogFetch` (`src/pages/catalog/shared.ts`), which carries the detail endpoints' `reason` — `not-found` or `missing-translation` — through to the screen rather than reducing it to a boolean. The discrimination the server makes is only worth making if it survives the trip: a screen that cannot tell an absent thing from an untranslated one has to guess, and guessing "absent" turns content the store holds into a dead end. A second fetch site is how two screens come to disagree about what a 404 means, exactly as a second locale-resolution site would about what language the visitor is reading.
- **Every screen renders the same shell, and the shell is a component rather than a route.** There is no layout route: `src/main.tsx` renders `useRoutes(routes)` over `vite-plugin-pages`' output directly, so a screen carries its chrome by rendering `StoreHeader` (or `AdminShell`, which is that header plus an administration label and a back-link). Two consequences follow and neither is incidental. A new screen is not given the header by the router — a screen that forgets it is a screen with no way out, exactly as fifteen of them were before this was a rule. And each screen mounting the header pays its reads: the session and the cart are fetched per screen, because there is no layout instance to hoist them into and per-visitor state may not be cached in the process (see the session constraint above). → [DESIGN.md § Page frame](./DESIGN.md#page-frame)
- **One content column width, declared once.** `src/components/layout.ts` exports the single class every screen's main content container uses; the four sign-on screens, which are centred cards rather than columns, are the only exception. Six widths were in use before it existed, which made the page shift sideways between two steps of one purchase. A repository-level Vitest file scans the screen sources and fails on a screen that declares its own, in the manner `src/theme-tokens.test.ts` already establishes for the colour tokens — a width is a property of the codebase rather than of any one component, so no component test observes it.
- **TypeScript is strict**, with complete annotations on exported functions.
- **`auto-imports.d.ts` is generated, not committed.** It does not exist on a fresh clone; the `prebuild` and `pretypecheck` hooks create it. Any new tsc-only script needs the same hook or it fails only on a clean checkout.
- **Vitest runs as two projects, chosen by path**: tests for server-side code (`routes/**`, `auth/**`, `account/**`, `catalog/**`, `admin/**`, `cart/**`, `order/**`, `payment/**`, `fulfillment/**`, `notifications/**`) run in the `server` project (node), everything else in `client` (jsdom). A test that reaches `db/client.ts` from the jsdom project cannot resolve `bun:sqlite` at all, so a new server-side directory must be added to the `server` project's include **and** the `client` project's exclude when it is created. Both lists name the directories literally; adding the directory to only one of them is the failure mode. A third list names them too: `tsconfig.node.json`'s `include`, without which `tsc --build` does not see the directory as part of the project at all. Three literal lists, one per tool, and none of them is derived from another — registering a new capability directory means editing all three.

## Deployment

- `ecosystem.config.js` (PM2) runs the real build — `.output/server/index.mjs`, under Bun, as the constraint above requires. `nitro.service` (systemd) is the non-PM2 equivalent with the same requirement.
- `Dockerfile` / `docker-compose.yml` build a static `dist/` served by nginx. They never run `.output/server/index.mjs`, so they do not serve the Nitro API or the database-backed routes; they are inherited from the template and are not a supported deployment target as they stand.

## Key Decisions

Decisions that bind work beyond the change that made them. Each is authored where it was made; this is the index, not the record.

- **The bootstrap stack is adopted as-is and is settled.** Structure, tooling, routing, styling and dependency choices came from the `ts-reactjs-vite-tailwindcss` template (provenance in `bootstrap-tmpl.yaml`) and are not revisited per sprint — re-scaffolding trades a verified foundation for an unproven one and forfeits the regression cover the template's own suites already carry. Changing any of them requires an explicit proposal. _Authored in change `swhm-i-0001-bootstrap-my-pet-store` (D1)._
- **One CI workflow covers every tier**, on every sprint-branch push. A second workflow would double every check run on every sprint branch, and a tier proven only locally is not proven at all — the browser tier cannot run in an engineer container, so CI is where it is observed. _Authored in change `swhm-i-0001-bootstrap-my-pet-store` (D4)._
- **Session state is a database row behind an opaque httpOnly cookie**, and is the one place per-visitor state belongs. H3 2 offers no session primitive, and the alternative — process memory — loses every visitor on a restart and cannot be shared. _Authored in change `swhm-i-0002-user-authentication-sign-on`._
- **An order records what was agreed, not a view of what is current.** Its addresses, contact details, prices, catalogue hierarchy and the locale it was placed under are copied onto the order and its line items at placement, never referenced from the account, the catalogue or the item. A later capability reading an order — payment, fulfilment, approval, notification — reads the order, and must not join back to restate it: a customer who moves house does not retroactively change where an order was shipped, a price change does not retroactively change what someone paid, and a customer who switches language does not move their own order across an approval threshold. This is why an account keeps one address while an order keeps two, and why the locale is a column on the order rather than a read of the profile. Anything an order is later judged by is copied at placement for the same reason. _Authored in change `swhm-i-0008-order-submission-checkout` (D2), extending the price-paid rule authored in `swhm-i-0006-administrative-operations-ma` and extended for locale in `swhm-i-0011-order-approval-workflow` (D2)._
- **A cart is cleared only after the order it became is committed.** Placement is a single transaction — order, line items, clear — so a failure at any point leaves the shopper's cart intact to retry, rather than an order with no lines or a cart emptied for an order that never existed. _Authored in change `swhm-i-0008-order-submission-checkout` (D4)._
- **An order is placed only after the payment for it is authorized.** Checkout runs authorize-then-place in that order, so a refused card and a declined authorization both leave no order behind and nothing to reconcile. The alternative — place, then authorize — makes an unpaid order a state the store has to model, chase and clean up, and every later capability that reads an order would have to know which kind it was looking at. Fulfilment, approval and notification inherit this: an order that exists has been authorized. What authorization does **not** mean is that money moved; settlement is not built (PRODUCT.md § Not yet decided). _Authored in change `swhm-i-0009-payment-credit-card-processi` (D6)._
- **A capability that moves an order toward shipment reads the approval decision first, and reads it positively.** Fulfilment acts only on an order that is APPROVED — not on any order that is "not yet completed" — and refuses before it commits anything, rather than after. Two properties of this failure make the positive test the only safe form. It is silent: every step of a fulfilment run over a denied order succeeds, so stock leaves the warehouse and an invoice is produced with nothing failing anywhere. And an exclusion list is correct only for the statuses that existed when it was written, which is exactly how a `DENIED` order became completable — the workflow gained two statuses and the list that predated them was never re-read. Anything later that ships, invoices, returns or re-opens an order inherits both halves. _Authored in change `swhm-s-0019-bugfix-swhm-t-0214-fulfilmen` (D1, D2)._
- **Anything outside this application is reached through an interface with an injected implementation**, never a direct call from the code that needs it, and ships with a stub the tiers below the browser can run against. The payment processor is the first and only such boundary (§ Integration points). This is also what keeps the card-number rule above enforceable: the boundary is the single place a real number may cross, so "the store never persists one" stays a property of the schema rather than a habit each caller has to keep. _Authored in change `swhm-i-0009-payment-credit-card-processi` (D5)._
- **Protected resources are declared in configuration and enforced by a single decision function**, consumed by server middleware and by the client route guard. One decision with two enforcement points is the only arrangement that covers both an API path and a client-side navigation to the same resource. _Authored in change `swhm-i-0002-user-authentication-sign-on`._
- **Credentials are stored hashed, never as plaintext**, even where an extracted legacy specification describes plaintext comparison. The specification's scenarios observe only whether authentication succeeds, so the deviation costs nothing it specifies and removes a standing exposure from every capability that follows. Deviations of this kind are recorded against the sprint rather than by editing the extracted spec. _Authored in change `swhm-i-0002-user-authentication-sign-on`._
- **Server-side capability code lives in its own top-level directory, outside the ones Nitro scans**, with its tests registered in Vitest's `server` project. A module placed under `routes/` becomes a public endpoint by existing, and one tested from the jsdom project cannot load the database driver at all. _Authored in change `swhm-i-0002-user-authentication-sign-on`._
- **A card number is never persisted.** The store holds a card's type, expiry and last four digits — enough to show a customer which card it already has — and reduces any number it is given to those four digits before storage. This holds even where an extracted legacy specification asks for the number, on the same reasoning as the credentials decision above. It binds every later capability: an order or payment flow that needs a real card number integrates a processor rather than reading one back from this database, which PRODUCT.md § Scope already requires. _Authored in change `swhm-i-0003-customer-account-profile-man` (D1)._
- **A paginated read returns a page and a `hasNext` flag, never a total count.** A page is read as `limit count + 1`: the extra row proves more results exist and is then dropped. Any capability that pages — orders, administrative lists — follows this rather than issuing a COUNT, which doubles the query cost to produce a number no screen has to show. It also fixes what a page is: an ordered window, so every paginated read needs a deterministic sort or the same row can appear twice. _Authored in change `swhm-i-0004-product-catalog-search` (D3)._
- **Translatable content lives in a per-locale detail row, not a column per language.** An entity row carries identity and untranslatable facts; a sibling `_details` row carries one locale's text, keyed on (entity id, locale). Adding a language is then data, not a migration, and "this content does not exist in that locale" is expressible — which a column-per-language schema cannot do without nulls that mean two different things. Every later localized entity follows this. _Authored in change `swhm-i-0004-product-catalog-search` (D2, D4)._
- **The catalogue is readable without a session.** No catalogue route reads the sign-on cookie, and the resource list in `auth/protected-resources.ts` is unchanged. Where the boundary between public browsing and a signed-on action sits is a decision each later capability makes explicitly, against that one list, rather than inheriting a default. _Authored in change `swhm-i-0004-product-catalog-search` (D6)._
- **A screen gated on a client-side read renders a pending state, never nothing.** The route guard keeps its contract — it still decides access from the one pure function and still redirects on a denial — but the undecided window is now observable instead of an empty document. A screen that renders nothing has two costs that compound: a visitor cannot tell a slow page from a broken one, and a browser test has no intermediate signal, so its only recourse is a blind timeout on the final content, which is what made `e2e/customer-profile.spec.ts` flaky. Every later protected screen inherits the guard, and every later client-fetching screen faces the same choice. _Authored in change `swhm-s-0006-multi-language-support` (D2, D3)._
- **A read that finds no localized content reports which fact was missing, not merely that one was.** An entity and its per-locale detail row are separate, so a `null` has two causes — no such entity, or no content for that locale — and the two owe a visitor different answers: one is a broken link, the other is an honest "not translated yet" with a way back to English. The detail endpoints therefore answer 404 with a `reason` of `not-found` or `missing-translation`; the status and the error text are unchanged, so the field is additive. This binds every later capability that reads localized content — an order, a cart, a notification each face the same ambiguity, and inferring the answer from "the locale is not the default" is wrong precisely when the id is also wrong. _Authored in change `swhm-i-0005-multi-language-support` (D1, `artifacts/SWHM-S-0007/PLANNING-NOTES.md`)._
- **A component never drives another component's state by synthesizing DOM events.** Where one screen region has to operate a control that lives in another, the state is lifted and passed as a callback, or the region renders its own instance — it does not find the other component's node and dispatch events at it. A headless component's open state is a machine reacting to a full pointer and focus sequence, not to a `click`, so a synthesized event is read as a different gesture and works only from a state the component has not been used from. The result is a control that works once per page load and cannot be covered by a unit test, because the failure needs a prior real interaction to appear. _Authored in change `swhm-s-0008-bugfix-found-by-inspector` (RC-2, D-5)._
- **A protected path may be denied to anyone, but only a navigation sets the return address.** The sign-on filter decides reachability from the path alone; what the request _is_ decides whether that path is remembered as the post-authentication destination. The two were one decision, and the cost was that any screen fetching a protected API in the background silently overwrote where its visitor would land after signing in — a bug with no failing request anywhere, because the fetch followed the redirect and got a 200. Every later capability that adds a protected resource inherits this: a resource can be both a page a visitor navigates to and an endpoint the client reads, and it is only the first of those that is somewhere to come back to. _Authored in change `swhm-s-0009-bugfix-swhm-t-0094-swhm-t-00` (RC-3, D5–D7)._
- **An account's entities share the customer's primary key rather than carrying surrogate ids.** The account, profile, contact information, address and card metadata are each 1:1 with the customer, so `user_name` is the key throughout and `ON DELETE CASCADE` expresses the ownership the legacy container did in code. Anything later that turns out to be 1:N — a second address, an order — takes its own key instead of widening one of these. _Authored in change `swhm-i-0003-customer-account-profile-man`._
- **A shared component never defaults a word the visitor reads.** Where one component renders prose for several callers, the prop that names the caller's subject is required, not defaulted — a default is a claim that the omitted value is correct, and for a noun describing the caller it is correct for exactly one caller. Every other one then type-checks, renders, passes its tests and says the wrong thing, which is a defect with no failing signal anywhere. This is not hypothetical: the same defaulted noun in the language-unavailable panel shipped the wrong word twice in two sprints, for the product screen and then for the category screen, each time because a new call site was not a caller the default's author had in mind. Requiring the prop turns "a later screen forgot something" into a compile error. _Authored in change `swhm-s-0011-bugfix-swhm-t-0105-category` (RC, D1)._
- **The capability that first needs an entity defines it, and later capabilities inherit the shape.** The order tables were created by the administrative capability, which only reads them, because the alternative was to leave a specified capability unbuildable until an unrelated one shipped. Reading an entity is a strictly smaller commitment to its shape than creating one, so the reader defining it is the cheaper mistake to correct. Cart, checkout, fulfilment and approval each extend `orders` and `order_line_item` rather than introducing a parallel set. _Authored in change `swhm-i-0006-administrative-operations-ma` (D1)._
- **The access decision answers two questions, and a missing role is not a redirect.** `evaluateAccess()` distinguishes "not signed on" from "signed on without the role this path requires", because the two owe different answers: the first is somewhere to come back to after signing on, the second is a refusal. Sending a signed-on user to the sign-on page because they lack a role produces a loop with no error anywhere — they authenticate successfully and are returned to a path that denies them again. The role lives on the identity record and the requirement lives on the resource entry, so adding a privileged path stays a configuration change rather than a new check, as the single-decision-function rule above requires. _Authored in change `swhm-i-0006-administrative-operations-ma` (D2, D3)._
- **A line item records the price paid, not a reference to the current price.** `order_line_item.unit_price` is written when the line is created, and every total is summed from it. A report that joins back to `item.list_price` silently restates history the moment a price changes — last quarter's revenue moves, with nothing failing and no way to notice. Any later capability that totals money reads the recorded price. _Authored in change `swhm-i-0006-administrative-operations-ma` (D4)._
- **Removing dependent rows is code's job, never the database's.** Foreign-key enforcement is off (§ Data model), so a capability that deletes a row deletes what depends on it explicitly, in the function that owns the deletion — not in each caller, which is how one path comes to leak rows the others clean up. Signing out clears the cart this way rather than relying on the cascade from `sessions`. The failure this avoids is silent in the worst way: the orphaned rows are unreachable, so nothing looks broken until something counts them. _Authored in change `swhm-i-0007-shopping-cart-management` (D4)._
- **Work the legacy application delivered asynchronously arrives here as a request.** Fulfilment was a message-driven bean on a JMS queue; it is `POST /api/fulfillment/process` taking an order id. No broker is introduced, and none should be introduced to restore an extracted specification's transport: this is one deployable with an embedded database, and a queue would add an operational component to buy a property nothing in the specification observes. Every later capability that was asynchronous in the legacy system — notification is the next — inherits this, and inherits the obligation the transport used to carry: because nothing retries, the operation itself must be safe to repeat. _Authored in change `swhm-i-0010-order-fulfillment-shipping` (D1)._
- **Stock is reduced when an order is filled, never reserved when it is placed, and a line ships whole or not at all.** A fulfilment run compares what is held against the line's full quantity, ships the lines it can, and leaves the rest untouched for a later run — so the pass is idempotent, a repeat cannot double-deduct, and an order reaches `COMPLETED` only when every line has gone out. The cost is deliberate and recorded in PRODUCT.md § Not yet decided: a shopper can order what the store cannot fill. Any later capability that acts on stock — a reservation, a backorder, a refusal at checkout — is changing this decision, not extending it. _Authored in change `swhm-i-0010-order-fulfillment-shipping` (D3)._
- **An order's status has terminal values, and a decided order is never re-decided.** `APPROVED`, `DENIED` and `COMPLETED` are terminal; only `PENDING` may be decided. A decision arriving for a terminal order is skipped and **reported as skipped** — not refused as an error and not silently dropped, because the two are indistinguishable to a caller and only one of them is true. This is what makes committing a decision safe to repeat, which is the obligation the queue decision below transfers to every capability that lost its transport: nothing retries, so the operation must tolerate being run twice. Any later capability that writes `orders.status` inherits the vocabulary and the guard rather than deciding again what a terminal state means. _Authored in change `swhm-i-0011-order-approval-workflow` (D3, D7)._
- **A handoff between two capabilities inside this deployable is a table, not a transport.** The supplier purchase order an approval produces is rows in the same database the fulfilment capability works from; the notification a decision owes a customer is a row a delivery capability will read. Neither is serialized, queued or sent, because both ends are in the same process and the same database — a document format and a transport would buy nothing any scenario observes, and would add an operational component to stand between two functions that can call each other. A boundary is declared in § Integration points only when something outside this application is genuinely on the other side. _Authored in change `swhm-i-0011-order-approval-workflow` (D4, D5)._
- **What the store contacts a customer at is resolved when it writes to them, not when the thing worth writing about happened.** A notification's recipient comes from the account's contact record at the moment it is sent, falling back to the address copied onto the order only when the account holds none. This is a deliberate, narrow exception to the copy-onto-the-order rule above, and the line between them is what the value is _for_: that rule protects what was **agreed** — a price, the address an order shipped to, the locale it was judged under — and none of those may move after the fact. An address to contact someone at is not an agreement, it is a current fact about a person, and a customer who changed it did so precisely so the store would use the new one. Anything later that reaches a customer rather than recording what they committed to inherits this. _Authored in change `swhm-i-0012-customer-notifications-commu` (D5)._
- **A derived total is computed on read, never stored.** A cart's line totals, subtotal and item count are calculated from its rows each time it is read. Storing them creates a second source of truth that every mutation has to remember to update, and the first one that forgets produces a total that is wrong with nothing failing. Any later capability holding a summable collection follows this until a measured reason says otherwise. _Authored in change `swhm-i-0007-shopping-cart-management` (D6)._
- **A screen asks who the visitor is by reading the session, never by probing a protected path.** `GET /api/signon/session` reports whether the visitor is signed on, their username and the role their identity holds, and it writes nothing. `GET /api/signon/check` answers the same question about a specific path but records that path as the post-sign-on destination as a side effect, so a screen that probed it to decide what to render would silently move where its visitor lands after signing in — the same failure mode the navigation-only return-address decision above was written for, arriving through a different door. Any later screen that needs to know something about the current identity extends the session read rather than adding a second probe. _Authored in change `swhm-i-0014-consistent-look-and-site-nav` (D2)._
- **A link shown only to those allowed to follow it is a convenience, never the protection.** The header offers an administrator the route to `/admin`; what keeps everyone else out is the resource list and the single decision function, enforced in the middleware and in the client route guard. Hiding a control is presentation, and presentation is reversible by anyone with a browser. This binds every later privileged surface: the decision to show a control and the decision to permit the action behind it are separate, and only the second one is access control. _Authored in change `swhm-i-0014-consistent-look-and-site-nav` (D4)._
